## 2. 출력 형태 — 마크다운(`content`) 구조

DI는 문서를 마크다운으로 재구성하되, 레이아웃 정보를 **HTML 태그와 주석**으로 함께 표현한다. 실제 서두(목차) 발췌:

```markdown
<!-- PageHeader="www.mpb.go.kr" -->

# 2025 회계연도 기금운용 평가보고서

<figure>
Ⅱ
</figure>

자산운용부문
2026\. 5\.

<!-- PageBreak -->

## 목 차

## Ⅰ . 2025회계연도 기금운용평가 자산운용부문 개요 1
1\. 평가의 목적
1
...
```

**등장하는 마커:**
| 마커 | 의미 | 파이프라인에서의 활용 |
|---|---|---|
| `# / ## / ###` | 제목·섹션 헤딩 | 섹션 경로(section_path) 구성 |
| `<!-- PageBreak -->` | 페이지 경계 | 물리 페이지 추적 |
| `<!-- PageNumber="- i -" -->` | 인쇄 페이지 번호 | printed page ↔ physical page 매핑 |
| `<!-- PageHeader="..." -->` | 머리말 | 노이즈로 제외 |
| `<figure>...</figure>` | 그림/로고 영역 | 그림 청크 처리 |
| `<table>...</table>` | 표 | 표 청크(별도 인덱스) |

## 4. 표(table) 표현 방식

표는 `content` 안에서 **`<table>` HTML**로, `caption`이 있으면 함께 나온다. 실제 예시(대규모 기금 평가의 등급 환산표):

```html
<table>
<caption>< 9단계 평가등급별 평점 ></caption>
<tr><td>등급</td><td>1</td><td>2</td>...<td>9</td></tr>
<tr><td>Z값</td><td>~- 2.1</td><td>-2.1~ -1.5</td>...<td>2.1~</td></tr>
<tr><td>평점</td><td>0.0</td><td>12.5</td>...<td>100.0</td></tr>
</table>
```

동시에 `tables[]` 배열에는 **셀 단위 구조**도 담긴다(좌표·스팬 포함). 예: 평가단 구성표는 `rowCount=19, columnCount=4, cells=59`, 첫 행 헤더 = `['구분', '성명 (출생)', '소속 및 직위', '학력 및 주요경력']`.

> 파이프라인은 표를 **별도 인덱스(search_tables)** 로 적재해, 수치·등급 질의가 표에 정확히 매칭되도록 한다.

## 5. 그림(figure) 표현

12개 `figures`는 각각 `boundingRegions`(페이지+폴리곤 좌표), `spans`, `elements`를 가진다. 대부분 표지 로고·차트 영역이며 caption은 대체로 없다(예: figure[0] = page 1, caption `None`).

> 그림은 `show_source_page`로 **원문 페이지 이미지**를 렌더링해 보여줄 때 활용된다(사용자가 원문 요청 시).

## 7. 이 출력이 파이프라인으로 이어지는 흐름

```
DI content/paragraphs/tables/figures
        │  ingest/parser.py: _result_to_parsed → ParsedDoc(문단/표/그림, offset)
        ▼
ingest/chunker.py: 문단·표를 offset 순 병합 → 레이아웃 인지 청킹
        │   · title/sectionHeading으로 section_path
        │   · pageNumber로 인쇄↔물리 페이지 매핑
        │   · 표는 <table> 그대로 → 표 청크
        ▼
Chunk[] → 임베딩 → AI Search 2개 인덱스(narrative / tables)
```

자세한 청킹·검색 과정은 [`ingest-pipeline-and-chunking.md`](./ingest-pipeline-and-chunking.md), [`pipeline-and-search-process.md`](./pipeline-and-search-process.md) 참조.

## 8. 파싱 품질 검증 (실측)

> 방법: **재호출 없이** `.ingest_cache/gicheum-2025-asset.json`(DI가 반환한 원본 응답 `result.as_dict()`를 그대로 저장)을 직접 분석. 캐시가 곧 DI 실제 출력이므로 추측이 아님. 크리티컬 항목 2가지(회전 페이지, 페이지 넘는 표)와 그 인덱싱 영향을 확인.

### 8.1 페이지 방향(회전) — ✅ 정상 해석 (8페이지 전수 확인)
- `pages[].angle` 분포: **0° × 523, −90° × 8, 1° × 1** (물리 크기는 전부 세로, unit=inch)
- **−90° 8페이지: p14~20, 28** — 가로로 눕힌 넓은 표(대형·중소형/대규모 기금 배점표 등)
- 전수 정합성 확인 — 8페이지 모두 표가 **논리 읽기순서대로 정상 파싱**:

  | 페이지 | 표 | 크기(행×열) | 내용 |
  |---|---|---|---|
  | p14 | #8 | 13×5 | 대형·중소형 배점표 — 자산운용 체계 |
  | p15 | #9 | 13×5 | 〃 전담조직 전문성 |
  | p16 | #10 | 14×5 | 〃 투자실행정책 |
  | p17 | #11 | 9×5 | 〃 위험관리 |
  | p18 | #12 | 16×5 | 〃 성과관리 |
  | p19 | #13 | 11×5 | 〃 중장기자산 수익률 |
  | p20 | #14 | 18×7 | 평가지표/실적현황/자산운용 성과/극단값 처리 |
  | p28 | #24 | 4×6 | 실적현황/운용수익률/위험조정수익률(1·5·20년) |

- 헤더 행·컬럼 정렬·셀 값 모두 정상. 관찰된 유일한 잡음은 **사소한 OCR 오타 1건**(p17 `"2, 자산운용 위험관리…"` — 마침표가 쉼표로 인식). 구조 파싱 오류가 아니며 검색에 영향 미미.
- 결론: DI가 회전을 **감지·정규화**(`angle=-90`)해 눕힌 표를 올바르게 해석함. 이 표들도 §8.3처럼 페이지별 표 청크로 정상 적재됨.

### 8.2 페이지를 넘는 표 — ⚠️ DI는 병합하지 않고 페이지별로 분리
- `boundingRegions`가 2개 이상 페이지인 표 = **0개** → DI는 페이지를 넘는 표를 **하나로 이어붙이지 않음**. 페이지별 **별개 표 객체**로 출력.
- 마크다운에서 `</table>` 직후 `<!-- PageBreak -->` 후 `<table>` 인접 = **10곳** (표가 페이지 경계에서 끊김).
- **완화 요인**: 연속되는 조각들이 다음 페이지에서 **헤더 행을 다시 반복** → **헤더 없는 고아 조각 = 0개**. 각 조각이 컬럼 라벨을 유지해 단독으로 의미가 통함.
  - 예: 대형·중소형 배점표가 p14→15→16…로 분리되지만 각 조각의 첫 행이 `대형(평잔 1조원 이상) | 배점 | 중소형… | 배점 | 투자풀 가점` 로 반복됨.

### 8.3 인덱싱 영향 — 분리된 표 = 별도 문서로 적재 (실측 확인)
청킹 실행 결과(`chunk_document`):

| 항목 | 값 |
|---|---|
| 총 청크 | 805 |
| **표 청크** | **199** (= DI 표 199개와 **1:1**) |
| 서술 청크 | 606 |

- `ingest/chunker.py:99-115` — 표 아이템마다 **정확히 1개 Chunk** 생성 (표 청크 = DI 표 객체 수).
- `ingest/indexer.py` `upload_chunks` — **1 청크 = AI Search 1 문서**.
- ⇒ **페이지로 분리된 표는 조각마다 별도 AI Search 문서로 적재된다.**
  - 실측: 배점표 한 논리 표가 표청크 `…-37(p14)`, `…-39(p15)`, `…-41(p16)` 로 각각 분리되며, 각 조각이 헤더를 반복 보유.

### 8.4 리스크와 완화

| 구분 | 내용 |
|---|---|
| 정보 손실 | **없음** — 분리 조각이 헤더(컬럼 라벨)를 유지 → 오정렬/맥락 상실 없음 |
| 잔여 리스크 | 하나의 긴 표가 **여러 문서로 분할** → "표 전체를 한 번에 집계"하는 질의는 일부 조각만 검색될 수 있음 |
| 현재 완화 | 시맨틱 리랭킹 + top-k 다중 조회(에이전트가 필요시 재검색) 로 대부분 커버 |
| 향후 옵션(필요 시) | 인접 페이지 동일 헤더 표를 청킹 단계에서 병합, 또는 표 청크에 "(N페이지에서 이어짐)" 메타 부여 → **§9에서 병합 구현함** |

## 9. 개선 — 페이지 분할 표 병합 (구현됨)

§8.2~8.3에서 확인한 "긴 표가 페이지별로 쪼개져 별도 문서로 적재되는" 문제를 청킹 단계에서 완화한다.

### 9.1 판별 휴리스틱

두 표가 **연속(continuation)** 인지 판단하는 조건 — **모두 충족**해야 병합:

| 조건 | 근거(§8 실측) |
|---|---|
| 직전 표 **바로 다음 물리 페이지** (`page == last_page+1`) | 연속 조각은 페이지 경계에서만 끊김 |
| **헤더 행(첫 줄)이 동일** | 연속 조각은 다음 페이지에 헤더를 반복 |
| 이어지는 조각에 **caption 없음** | 연속 조각은 caption이 없다(캡션은 표의 첫 조각에만) |

핵심 신호는 **caption**이다. 검증 데이터에서:

| 사례 | 헤더 | caption | 판정 |
|---|---|---|---|
| 배점표 p14→15→…→19 (#8→#13) | 동일 | 첫 조각만 있음, 이후 없음 | **병합** ✅ |
| 평가단 명단 #1→#2 | 동일 | 이어지는 조각 없음 | **병합** ✅ |
| 참고7 vs 참고8 (#31/#32) | 동일 | **둘 다 있음** | 별개 유지 ✅ |
| 자산군별/운용수익률 현황 (#89/#90) | 동일 | **둘 다 있음** | 별개 유지 ✅ |
| 서로 다른 표 (#188/#189) | 다름 | — | 별개 유지 ✅ |

→ 헤더만 보면 참고7/참고8 같은 **별개 표를 오병합**하지만, caption 신호를 더하면 정확히 구분된다.

### 9.2 병합 동작
- 이어지는 조각의 **헤더 행 + 구분선(`|---|`)을 제거**하고 **본문 데이터 행만** 앞 표에 이어붙인다.
- 시작 페이지·caption은 첫 조각 것을 유지 → 하나의 표 청크 = 하나의 AI Search 문서.

### 9.3 구현 위치
- `ingest/parser.py` — DI 표의 **caption을 `ParsedTable.caption`에 보존**(판별 신호 + 표 캡션이 청크에 포함돼 검색 컨텍스트도 향상).
- `ingest/chunker.py` `merge_continuation_tables()` — 위 휴리스틱으로 연속 표 병합. `chunk_document`가 표 스트림 구성 전 호출.

### 9.4 실측 효과

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 표(ParsedTable) 수 | 199 | **191** (8개 병합) |
| 표 청크 = AI Search 문서 | 199 | **191** |
| 총 청크 | 805 | 790 |
| 배점표 chain(p14~19) | 6개 청크 | **1개 청크**(헤더 1회, 전 페이지 행 통합) |
| 참고7/참고8 등 별개 표 | 유지 | **유지**(오병합 없음) |

### 9.5 전제·한계
- caption 없는 서로 다른 표가 **인접 페이지 + 동일 헤더**로 나란히 오면 오병합 가능(드묾). 이 문서에서는 해당 사례 없음.
- 3페이지 이상 연속도 순차적으로 병합됨(배점표 chain으로 검증).

## 10. 한 줄 요약

DI(`prebuilt-layout`)는 532p PDF를 **731,412자 마크다운 + 18,963 문단 + 199 표 + 12 그림 + 532 페이지** 의 레이아웃 인지 구조로 변환했다. 마크다운 전문은 [`reports/di-raw-markdown-full.md`](./di-raw-markdown-full.md)에서 그대로 확인할 수 있고, 이 구조가 청킹·검색 품질의 출발점이 된다.
