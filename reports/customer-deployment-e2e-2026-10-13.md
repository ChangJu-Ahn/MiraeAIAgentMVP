## 실제 실행 경로

1. 공개 main을 기존 작업 디렉터리와 별도의 경로로 clone
2. 로컬 `.env`, 기존 서비스 키, 이전 Function runtime ZIP 없이 `uv --frozen` 환경 생성
3. 문서의 `--check` 명령 실행 — 로그인·모델/SKU·quota·Bicep 컴파일 통과
4. 최초 `--yes` 명령으로 신규 RG 생성 및 리소스 배포
5. 실제로 드러난 패키지 오류를 수정하고 동일한 고객용 명령으로 재실행

최초 명령:

```bash
uv run --python 3.12 --frozen python scripts/deploy_demo.py \
  --resource-group rg-mirae-customer-e2e-20261013 \
  --subscription 347e0df7-94e9-4feb-b42d-57d7e49566f2 \
  --yes
```

사용자의 조직 정책 조건을 명시한 재실행:

```bash
uv run --python 3.12 --frozen python scripts/deploy_demo.py \
  --resource-group rg-mirae-customer-e2e-20261013 \
  --subscription 347e0df7-94e9-4feb-b42d-57d7e49566f2 \
  --resource-tag SecurityControl=Ignore \
  --yes
```

`SecurityControl=Ignore`는 모든 고객에게 자동 부여하는 값이 아니다. 조직에서 허용한 정책 예외 태그를 사용자가 명시한 경우에만 전파한다.

원본 PDF를 물리적으로 분할해서 다시 올리는 대신, worker가 **25페이지 단위 DI 분석** 결과와 그림 작업을 Blob에 저장하고, 전체 문서의 기금 검증을 유지한 뒤 **16청크 단위 임베딩/적재**로 처리했다. 완료한 문서에는 pending marker가 남지 않았고, 각 완료 작업의 `error`는 `null`이었다.

이 처리 구간의 Azure Monitor `MemoryWorkingSet` 5분별 최대값 중 최고는 **432,642,389바이트(약 412.6 MiB)**였다. 이번 테스트에서 worker를 고의로 재시작하는 장애 주입은 하지 않았다.

## 최종 패키지의 동일 명령 재실행

푸시된 소스를 다시 clean clone한 뒤 `4fcdf89`까지 fast-forward했다. tracked source 수정이나 `.env` 없이, 위와 **동일한 고객 명령**을 23:07:08–23:16:27 KST에 재실행해 **9분 19초, exit 0**으로 완료했다. `--reasoning-capacity`를 따로 주지 않았으므로 교정된 기본값 자체를 검증한 것이다.

이번 재실행에는 리소스/모델 갱신, 고객 ACR의 Function 패키지 빌드, API 키 모드의 ACR credential 조회/아티팩트 digest 검증, ZIP 배포, 인덱스/이벤트 갱신, 챗봇 이미지 빌드, 샘플 업로드/완료 확인이 모두 포함됐다. 수동 runtime ZIP, 로컬 Docker, 기존 키리스 환경의 ACR 또는 서비스 키를 사용하지 않았다.

| 재실행 전후 비교 | 결과 |
|---|---|
| 5개 원본의 SHA-256 / ETag / 문서 fingerprint | 그대로 유지 |
| 문서별 청크 수 / 인덱스별 레코드 수 | 그대로 유지 |
| 선택한 본문·표·그림 내용/출처 필드의 레코드 digest | 그대로 유지 |
| 전체 catalog / fact 레코드 digest | 그대로 유지 |
| PDF/PNG 링크, hybrid 검색, 모집단/출처 검증 | 다시 통과 |
| 그룹에 패키지가 생성한 RBAC 할당 | 다시 0개 |
| 실제 reasoning 용량 | 100, 관리 API에서 **100 RPM / 100,000 TPM** 확인 |

처리 중인 원본 작업이 없는 것을 확인한 뒤 재실행했다. 원본 5개를 다시 업로드하거나 인덱스를 초기화하지 않았고, 기본 샘플은 동일 내용으로 재업로드되어 이전 완료 결과를 재사용했다.

**범위 구분:** 최초 신규 RG 실행에서 발견한 실패를 수정하여 동일 신규 그룹을 완성했고, 최종 패키지는 이 그룹의 재실행까지 검증했다. 최종 수정본으로 두 번째 빈 RG를 추가 생성하거나 별도 신규 구독을 생성한 시험은 하지 않았다.

## 실제 챗봇 16문항 결과

최종 배포의 Chrome 브라우저에서 문항마다 새 대화를 생성하고, 실제 입력·전송·WebSocket 답변 완료를 확인했다. 각 문항은 300초 제한으로 비어 있지 않은 답변, `E_STREAM` 부재, 주요 값/키워드와 출처 표기를 검사했다. 자료 부재/평가 대상 오류인 8·9번은 불가능한 원문 인용을 필수로 요구하지 않았으나, 실제 답변은 각각 문서 목록/기금 목록 출처를 제공했다.

**최종 16/16 통과, `E_STREAM` 0건.** 질문 전송 후 응답 완료까지 평균 **19.6초**, 중앙값 **12.35초**, 최대 **81.8초**였다. 최초 용량 10 시험은 14/16이었고 실패를 숨기지 않았으며, 용량 100 배포 후 실패 두 문항만이 아니라 **전체 16문항을 다시 실행**했다.

이 표는 **기능·대표 사실 assertion 및 답변 확인** 결과다. Evaluation의 5개 LLM-judge 품질 점수를 재측정한 결과, 모든 문장의 전문가 검수 또는 인용 번호의 전면 정합성 검증을 뜻하지 않는다. 긴 여러 도구 집계 답변에는 도구 결과별 인용 번호가 반복되어 표시되는 사례가 있어, 인용 번호 UX/정밀 품질 평가는 별도 점검 대상이다. 문항 14의 81.8초도 그대로 기록했으며, 항상 빠른 응답을 보장하지 않는다.

## 운영 범위와 비용

새 환경과 PDF 5개·기본 샘플은 검토할 수 있도록 **삭제하지 않고 유지**한다. Search Basic, Function B1, ACR Basic, Container Apps 최소 replica 1개, Storage/모니터링 및 DI/모델 호출 비용이 발생한다. 실제 청구 금액은 이번 시험에서 산정하지 않았고, reasoning 용량 100은 이 GlobalStandard 모델의 사용 가능한 quota/처리율이며 무료 사용이나 고정 청구액을 뜻하지 않는다.
